# 근거 정규화와 확장 지표의 공통 계약 제안

상태: UME-0 설계 근거. UME-1의 별도 계약은
[`evidence_result.v1`](../../contracts/evidence_result.v1.schema.json)과
[`metric_definition.v1`](../../contracts/metric_definition.v1.schema.json)에 저술했고,
[공개 적합성 벡터](../../fixtures/conformance/ume1/README.md)로 검토한다. 이 문서는
그 계약의 근거이며 새 CLI·투영기·수용 API의 구현 완료를 뜻하지 않는다.
작성일: 2026-10-14. 범위: underwrite의 입력·출력과 goppi 연계의 의미 경계.
goppi 측은 이 공통 계약을 읽기 전용으로 따라가고, 출처·개인정보·중단 복구·판정 의미는
자기 저장소에서 해결하겠다는 의견을 전했다. UME-0 조사와 UME-1 계약 저술에서
underwrite는 goppi 저장소를 읽기만 했다. goppi의 계약 채택과 자체 구현은 별도
결정이며, 앱·코어 패키지 버전, 공개 CLI, 기존 계약은 바뀌지 않는다.

## 먼저 반박할 가정

“어떤 데이터든 같은 지표로 정규화”는 성립하지 않는다. 원본에 사건 정의, 단위, 계획
모집단, 라벨 출처가 없으면 파서가 그 사실을 만들어낼 수 없다. 어떤 도구의 0.8은
성공 확률일 수도, 임의 루브릭 점수일 수도, 순위 점수일 수도 있다. 모두 0–1로
변환해도 구성개념과 참조 모집단이 같아지지 않는다. OpenInference의
[평가 주석 규약](https://github.com/Arize-ai/openinference/blob/main/spec/annotations.md)도
score의 의미·범위·방향이 평가자와 지표에 달려 있다고 명시한다.

“기본 지표 고정”도 모든 입력의 숫자 칸을 채운다는 뜻이면 위험하다. 계획 목록이 없는
파일의 coverage, 독립 라벨이 없는 판단기의 정확도, 결과 이후에 낸 점수의 사전
확률 보정은 측정할 수 없다. **고정할 것은 근거를 설명하는 항목과 조건부 지표의
적용·측정·미측정 규칙**이다. 누락된 값은 0이 아니고, 해당 없음은 성공이 아니다.

“확장지표 자유롭게”는 지표를 정의·가져와 검토할 자유와, 그 지표로 통과를
결정할 권한을 분리해야 한다. 공급자가 작성한 지표는 처음에 원천 주장이다.
공식·정답·모집단을 독립적으로 확인한 측정과 같은 권한을 주지 않는다.

## 사용자에게 줄 결과

코딩 에이전트가 서로 다른 평가 산출물을 로컬에서 받았을 때, 각 자료에 대해
“어떤 실행·사례·구성개념에 관한 주장인가, 실제로 무엇이 관측됐고 무엇이 부족한가,
어떤 지표가 적용 가능한가, 다음 검토에는 무엇이 필요한가”를 하나의 구조화된
근거 형식으로 받아야 한다. 사용자는 원본 파일과 판단 근거를 따라갈 수 있어야 한다.
제안하는 새 공통 결과의 기본 JSON에는 원문·개인 라벨·절대 경로·원천 예외 문장을
넣지 않는다. 구조 좌표, 불투명 참조, 해시, 제한된 사유 코드와 범위가 정해진 수치만
낸다. 기존 CLI 전체가 이미 이 개인정보 규칙을 만족한다는 뜻은 아니다. 전체 원본은
사용자가 명시적으로 지정한 비공개 로컬 저장소에만 보존하고, 자동 공유나 재게시를 하지 않는다.
원천 locator와 확장 메타데이터도 수신한 개인 정보를 그대로 출력하지 않도록
수용 경계에서 제한한다. goppi의 개인정보 정책과 별개로 이 출력·보존 경계는
underwrite가 책임진다. 상위 처리 결과는 분석 가능·근거 부족·지원되지 않음으로 구분한다.
“지원되지 않음”은 의미적 정규화의 성공이 아니다.

서로 다른 자료가 같은 형식으로 출력됐다고 결과 숫자를 합치지는 않는다. 단일 사례의
근거 목록과 비교 가능 조건을 보여 주되, 실제 측정과 변경 수락은 각 정책의 경계를
따른다. 제품 가치는 이 결과가 검토자의 잘못된 안전 추천을 줄이는지로 측정한다.
[판단 모델 연구의 대조 설계](judgment-models-product-fit-2026-10-14.md#경쟁자-대비-가치가-있는지-반증-가능한-시험)가
그 확인 방법의 출발점이다.

## 고정 핵심: 점수 목록보다 근거 항목

아래 다섯 항목의 **필드 의미와 상태 규칙**을 고정한다. 수치 계산은 필요한 선언과
입력이 있을 때만 한다. 상태·결손 이유·원본 좌표를 모든 항목에 남긴다.

| 고정 항목 | 확인할 사실 | 수치가 가능한 조건 |
| --- | --- | --- |
| 입력·정체성 | 지원 형식/버전, 원본 바이트 해시, 출처 참조, 대상 실행·사례 | 해시는 바이트 동일성만 확인한다. 생산자 인증에는 별도 근거가 필요하다. |
| 의미 | 구성개념·사건·단위·방향·표본 단위, 루브릭·라벨 출처와 버전 | 선언의 해시는 선언 동일성만 확인한다. 의미의 타당성이나 라벨의 진실은 증명하지 않는다. |
| 모집단 | 계획한 대상과 실제 관측, 누락·오류·중복·예상 밖의 사례 | 계획 모집단을 알 때만 계획 대비 coverage를 계산한다. 관측 수로 계획 수를 대신하지 않는다. |
| 적용·가용성 | 질문/지표의 해당 여부, 관측 0, 기권, 오류, 미측정 이유 | 적용 분모가 명시된 질문에만 적용률을 낸다. 모두 해당 없음이면 “좋은 점수”가 아니다. |
| 해석·권한 | 원천 주장, 독립 확인, 측정 결과, 정책·방법 정체성, 제한과 다음 입력 | 측정 지표의 통과·경고는 해당 프로필 안에서만 해석한다. 승인·배포 권한을 의미하지 않는다. |

상태 차원은 서로 접지 않는다. 입력이 지원되지 않는 일, 실제 값 0, 관측 누락,
수집 오류, 해당 없음, 모델 기권, 통계적 미측정, 수락 미결정은 각각 다른 사실이다.
기존 underwrite의 not_measured·indeterminate·abstained도 별도 의미를 유지한다.

| 직교 차원 | 구별할 값의 예 | 잘못된 병합 |
| --- | --- | --- |
| 입력 처리 | 분석 가능 / 근거 부족 / 미지원 | 파싱 실패를 성공적인 정규화로 표시 |
| 값의 존재·크기 | 원천에서 실제 관측한 0이나 1 / 값 없음 | 0과 값 없음의 혼합 |
| 적용 여부 | 적용 / 해당 없음 / 알 수 없음 | JevEval의 원천 총점 1을 질문 전부 적용으로 간주 |
| 가용성 | 관측 / 누락 / 오류 / 기권 | 오류나 기권을 0점으로 표시 |
| 확인 범위 | 바이트 계산, 선언 결합, 계획 모집단 대조, 계산 재현, 독립 라벨 확인을 각각 근거·방법·대상 범위에 연결 | 단일 verified 불리언으로 출처 인증·정답까지 암시 |
| 값의 출처 | 생산자 주장 / underwrite가 계산한 결과 | 공급자 점수를 자체 측정으로 이름 변경 |
| 사용 효력 | 기술 / 참고 / 해당 프로필 read가 허용한 효과 | source claim이라는 출처 종류와 advisory라는 허용 효력을 한 enum으로 합침 |

독립 확인을 표시한다면 무엇을 어떤 파일·방법·사례 집합에서 확인했는지 함께 적는다.
바이트를 해시했다는 사실은 그 바이트를 누가 생성했는지, 라벨이 참인지와 무관하다.
아래는 현행 CLI 형식이나 승인된 schema가 **아닌**, 실제 DeepEval 4.2.8 합성 export를
설계 차원으로 펼친 축약 예다.

- 원본: deepeval.test-run / 4.2.8, 바이트 해시
  sha256:5050efd8a89c8ee841237341383f73af590b778643f96da4e971ad534e23abbd.
- 대상: case_index 0. 원천이 안정적인 case ID를 제공하지 않았으므로 외부 사례와의
  연결은 미확인. 관측 사례는 1, 계획 사례 수와 예상 대비 coverage는 미측정.
- 지표 zero: 원천의 score 0을 관측한 source claim. 누락이 아님. 독립 라벨 확인과
  결과 전 확률 선언이 없으므로 정확도/보정은 미측정이며 판정 효력은 참고에 한정.
- 같은 사례의 지표 error: score 0이 아니라 원천 평가 오류. 지표별 결손 사유와
  다음 필요한 원천 자료를 남긴다.

이 예는 전역 품질 점수나 모든 도메인에 쓰는 성과 계산식이 아니다. 예를 들어
현재 [read.v2](../../contracts/read.v2.schema.json)의 event rate는 관측한 이진 사건에서,
all-k 진단은 필요한 완전 모집단과 표본에서, Brier/ECE는 동일 사건의 결과 이전 확률·
짝지은 라벨과 충분한 구간 표본에서만 측정된다. [event_read.py](../../src/underwrite/measurement/event_read.py)는
그 조건이 없으면 미측정 이유를 남긴다. 이 조건을 새 입력 형식에 맞춰 약화하지 않는다.

## 확장 지표: 선언은 열고, 측정·판정은 근거에 묶는다

확장 지표의 뜻을 재현할 수 있도록 다음 정의를 버전과 함께 명시한다:
namespace와 지표 ID, 구성개념/추정 대상, 사건 또는 라벨 정의, 값의 종류·범위·단위·
바람직한 방향, 표본 단위와 예상 모집단, 적용/결측/오류/기권 규칙, 집계 방법,
루브릭/라벨 출처, 필요한 입력 좌표, 사용한 계산 방법·정책·임계값. 확률이라면
어느 사건의 결과 **이전에** 예측했는지도 필요하다. 정의의 semantic digest와
실제로 계산한 방법/구현의 정체성은 별도로 묶는다. 같은 이름이나 같은 0–1 범위가
같은 지표라는 근거는 아니다.

제안하는 확장 경로는 두 가지다.

1. **선언·외부 계산 값 수용 제안:** 사용자가 namespace/버전 아래 새 지표를
   정의하고 다른 도구에서 계산한 값과 원본을 첨부할 수 있게 한다. 알려지지 않은
   파일 형식은 사용자가 명시적으로 추출한 claim과 원본 바이트 식별을 별도 입력으로
   내게 할 수 있다. 이는 원본 내용의 검증이 아니라 사용자 선언 경로다. 임의
   파일에서 지표를 추측하거나 공급된 코드를 자동 실행하지 않는다. 제안하는
   결과는 값을 source claim으로 보존하고, 수용 경계가 확인한 범위를 별도 근거로
   기록하며, 허용 효력은 advisory 이하로 둔다. 뜻을 모르는 숫자를 보정된 확률이나
   통과로 바꾸지 않는다. 미지원 구조에는 타입이 있는 거부/부족 상태와 다음 행동을
   계획한다. 이 경로는 현재 구현된 CLI 기능이 아니다.
2. **underwrite가 직접 측정:** 실제 사용자 과제에서 필요해지면 버전이 고정된 순수
   계산과 자격 검사를 추가한다. 동일한 의미·실패 규칙은 한 소유자가 계산하고,
   도메인별 의미는 프로필 안에 남긴다. 임의 Python 모듈·외부 스키마·수식 문장을
   untrusted 입력에서 자동 실행하는 범용 플러그인 엔진은 기본 경로가 아니다.
   계산이 성공해도 정책과 독립 근거 없이는 자동 수락 권한이 없다.

확장 지표를 사후에 재정의하면 기존 ID의 값만 고치지 않는다. 새 의미 버전과 digest로
별개 결과를 만든다. 사용자가 선택한 비공개 저장소에는 원본 점수·라벨과 정규화 결과를
함께 보존할 수 있다. 기본 결과에는 제한된 수치와 불투명 라벨 참조만 내고, 변환 방법과
손실된 정보를 명시한다. 지표가 여러 개여도 단위·사건·대상·모집단·방법의 의미가
같다는 근거 없이는 평균·순위·가중 통합을 하지 않는다.

| [기존 goppi baseline 투영](../../src/underwrite/instrument/evidence/goppi_baseline.py) | 버전이 지정된 완료된 교환 파일에서 native event observation으로 투영 | 새로운 공통 런타임 대신 이 실제 교환 파일로 호환·결손 사례를 먼저 검증한다. |

두 저장소의 구현 언어는 Python과 TypeScript다. 공유할 것은 실행 코드가 아니라
**버전이 있는 결과·확장 지표 파일 계약과 의미 테스트 벡터**다.
이번 작업의 공통 결과/확장 계약 저술 정본은 underwrite가 맡는다. goppi는 자체
실행·측정·게이트 의미, 원본 교환, 출처·개인정보·중단 복구의 정본을 유지한다.
이번 설계는 goppi 코드를 읽기 전용으로 참조했다. goppi의 검토나 채택이 완료됐다는
뜻은 아니며, goppi의 구현이나 안정 판정을 바꾸라는 지시도 아니다.

Underwrite의 첫 정본은 기존 observation.v1/read.v2를 고치지 않는 별도 버전 계약으로
만들고, 실제 입력에서 검증된 필드·상태만 담는다. goppi가 나중에 이를 직접
생산하려면 계약의 커밋·해시와 conformance 벡터를 핀하고 자체 export를 검증한다.
공개 클론에 형제 체크아웃이나 새로운 공통 런타임을 요구하지 않는다. 계약 내용
자체는 아래의 실제 작업과 두 저장소의 검토 근거를 보고 확정한다.

## 첫 검증 과제와 채택 조건

**사용자 작업:** 에이전트에게 지원되는 두 생산자의 실제 내보내기 파일을 주고
“각 실행·대상·지표에 대해 무엇을 알며, 무엇이 부족하고, 다음 검토 입력은 무엇인가?”
를 한 JSON으로 답하게 한다. 먼저 현재 CLI 결과와 원본을 연결해 시도한다.
goppi baseline v2의 실제 완료 교환은 로컬에 있으며, underwrite가 이미
project-baseline→observation.v1→read.v2 경로로 소비했다. 원본 경로와 내용은
비공개다. 이 소비 사실은 새 공통 계약의 검증이나 독립 정답의 근거가 아니다.
원천들의 점수 의미가 같다고 가정하지 않고, 연결 키가 없으면 관계를 미확인으로
출력한다. 실제 사용자의 반복 수작업 오류를 본 뒤에만 별도 투영 계약이나 명령을 추가한다.

계약 검증에는 최소한 다음 사례를 포함한다.

- 실제 0점과 관측 누락을 구별한다.
- JevEval에서 질문 전부 해당 없음인데 원천 최종점수가 1인 경우를 성공으로 승격하지 않는다.
- 계획 모집단이 없으면 계획 대비 coverage를 미측정으로 둔다.
- 같은 metric 이름이라도 루브릭·단위·표본 단위가 다르면 별개 의미로 둔다.
- 출처 해시만 맞고 라벨이 자기 신고이면 독립 정답으로 취급하지 않는다.
- goppi의 endpoint 실패 false와 infrastructure missing을 섞지 않는다.
- 미지원·모호한 형식은 허위 정규화 대신 타입이 있는 오류/부족 상태를 낸다.

구조적 채택 기준은 위의 근거 부재/미지원/해당 없음이 통과나 0점으로 바뀐 사례
0건, 지원 사례의 원본 좌표·분모·상태 불일치 0건, 기존 관측·read·goppi 교환
바이트와 판정 상태 회귀 0건이다. 이는 결과의 진실성을 입증하는 기준이 아니다.
제품 가치 기준은 [경쟁 비교 계획](judgment-models-product-fit-2026-10-14.md#경쟁자-대비-가치가-있는지-반증-가능한-시험)대로
같은 원본과 정책을 준 생산자 도구·현재 underwrite·작은 공개 스크립트를
독립 정답이 있는 새 사례에서 비교하는 것이다. 정답은 검토자에게 숨기고
검토자와 사례를 균형 배치한다. 잘못된 안전 추천이 줄면서 정상 수용·보류·
시간/비용의 사전 허용 범위를 지켜야 한다. 이득이 없으면 범용 추상화를
구현하지 않는다.

## 보류 중인 설계 결정

- 어느 실제 사용자 작업에서 현재 CLI 조합이 반복해서 실패하는지.
- 처음 필요한 최소 생산자 프로필과 그 원본 파일에 계획 모집단·질문 적용 정보가
  실제로 있는지. DeepEval JevEval의 런타임 score_breakdown이 저장된 TestRun에
  들어가는지는 [앞선 조사](judgment-models-product-fit-2026-10-14.md#이번-조사에서-확인하지-못한-것)에서도
  확인하지 못했다.
- Underwrite가 저술할 첫 버전 계약에 실제 어떤 필드와 오류 사유가 필요한지.
  goppi의 현행 영수증/해시·stable gate 의미는 별도 소유로 유지한다.

이 문서는 승인된 제품 스키마가 아니다. UME-1 스키마와 공개 적합성 벡터가 별도
정본이며, 현재 새 공통 결과를 생성·수용하는 CLI나 라이브러리 경로는 없다. goppi의
계약 채택이나 안정 판정도 완료됐다고 주장하지 않는다. UME-2 이후의 CLI/확장
구현은 반복되는 사용자 오류와 대조 실험의 결과에 따라 따로 결정한다.
