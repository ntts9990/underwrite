# 판단 기반 평가 모델의 underwrite 제품 적합성 조사

조사일: 2026-10-14. 범위: 공개 1차 자료, 현재 underwrite 코드·계약, 공개 벤치마크. 새로운 모델 호출, 유료 API 호출, 패키지
설치, goppi 수정은 하지 않았다. 이 문서의 성능 수치는 명시하지 않는 한 해당 연구 저자 또는 제품 공급자의 실험 결과다. underwrite에서
재현하거나 사용자 가치를 측정한 수치가 아니다.

## 결정

**지금 AnyJev 또는 JevEval을 underwrite의 내장 판정 엔진으로 도입하지 않는다.** 두 도구는 의미 있는 판단 결과의 후보
생산자이지만, 모델을 한 번 호출하거나 점수를 수입하는 것만으로는 underwrite의 목표인 “검증되지 않은 결과의 검증 통과 차단”이 나아졌다는 증거가
없다. 특히 외부 모델이 낸 점수, 문장, 확률, confidence를 실제 사건의 정답이나 보정된 확률로 승격해서는 안 된다.

가장 유망한 제품 후보는 **판단 결과의 적격성 검사와 대조 가능한 근거 보존**이다. 에이전트 실행의 성공과 부작용에 대한 판단을 모델·질문·루브릭·적용
여부·원본·독립 정답과 함께 보존하고, 현재 근거만 받은 사람 또는 에이전트의 후속 추천이 실제 실패·부작용을 놓치는지, 같은 과제에 판단 근거를 추가했을
때 이를 줄이는지 측정하는 방향이다. underwrite 자체는 안전 승인이나 병합 결정을 내리지 않는다. 이 가설은 아직 검증 전이다. 독립 라벨과 실제
실행 기록이 준비되기 전에는 새 어댑터, 판정 게이트, 런타임 의존성을 만들 근거가 없다.

## 제품이 해결할 일과 측정할 구성개념

사용자는 평가기마다 생성한 점수가 많아도 변경 후보를 안전하게 검토할 근거가 부족하다. underwrite의 현재 가치는 원본 바이트와 원천 주장,
모집단·누락, 명시한 측정 정책, 수락 분류를 구별하는 데 있다. 판단 모델을 더하면 다음 구성개념을 따로 취급해야 한다.

| 구성개념 | 관측 가능한 것 | 그 자체로 알 수 없는 것 |
| --- | --- | --- |
| 판단 결과 | 해당 입력에 대한 모델의 라벨·확률·점수와 질문별 값 | 정답, 모델 적격성, 독립 출처 |
| 일관성 | 순서·반복·문구 변화에 따른 판정 차이 | 사람 정답과의 일치 |
| 보정 | 사례 모집단에서 같은 사건의 결과 이전 예측 확률과 독립 결과 라벨의 발생 빈도 일치 | 다른 사건·영역·미래 분포에서의 보정 |
| 기권·적용 여부 | 답하지 않은 항목과 실제 적용한 질문의 비율 | 전체 품질의 자동 통과 |
| 제품 가치 | 동일 사례·검토 예산에서 잘못된 통과 감소, 정상 통과 유지, 검토 부담·비용 | 벤치마크 순위만으로 얻는 보편적 우월성 |

underwrite에는 이미 AB/BA 제시 순서 불일치, 다중 평가자 일치도, 근거 유무별 기권을 계산하는
[순수 판단 근거 모듈](../../src/underwrite/instrument/evidence/judge.py)이 있다.
[보정 계산](../../src/underwrite/measurement/calibration.py)은 이전 read 프로필에서 사용하는 순수 계산으로,
적법한 확률·이진 라벨 쌍에 Brier와 ECE를 제공한다. 이 계산이 있다고 해서 현재
[네이티브 측정](../../src/underwrite/measurement/event_read.py)이 외부 판단 점수를 자동으로 수용하거나 측정
read로 승격하는 것은 아니다. 현재 측정은 명시한 이진 사건과 정책만 수용하며, 제품 CLI는 판단 모델의 적격성을 판정하지 않는다.

[에이전트 사용 지침](../../AGENT_USAGE.md)은 외부 평가 산출물을 원천 주장과 바이트 식별로 다룬다.
[수락 단계](../../src/underwrite/acceptance/decision.py)는 사람 검토를 요구하고 병합 권한을 내지 않는다. 이것이
통합 시 보존해야 할 경계다.

## AnyJev와 JevEval은 서로 다른 공급 경로

| 경로 | 현재 동작과 근거 | underwrite 관점 |
| --- | --- | --- |
| AnyJev의 Decider | 공개 인과 언어 모델의 다음 토큰 분포에서 제한된 선택지의 확률을 읽는다. raw와 L0를 제공한다. L0는 선택지 회전과 라벨 선호 보정으로 제시 순서 편향을 줄이지만, 사람 라벨에 맞춘 확률 보정은 하지 않는다. [정본 저장소](https://github.com/nokia-applied-research/AnyJev), [기술 보고서](https://arxiv.org/abs/2610.00831) | 로컬 또는 공급자 측에서 쓰는 후보 생산자. 큰 모델·토크나이저·추론 환경을 underwrite 런타임에 넣을 이유는 없다. |
| AnyJev의 Tacit | 자체 증류 모델을 별도 체크포인트로 제공한다. 한 번의 forward 판정과 제한된 비율의 추론 단계 상승 경로가 있다. 이 경로는 L0의 순서 평균과 다르다. [README](https://github.com/nokia-applied-research/AnyJev), [제약](https://github.com/nokia-applied-research/AnyJev/blob/main/docs/limitations.md) | 별도의 모델·환경·비용 비교 대상. raw/L0와 Tacit 수치를 하나의 “AnyJev 성능”으로 합치면 안 된다. |
| JevEval | DeepEval이 Noul·Score·Choice 질문별 분포를 가중 평균 점수로 합친다. score_breakdown에 적용 여부와 분포를 둔다. 공식 기본 Jev 경로는 TypeSafe SDK·API 키를 사용한다. 사용자 제공 DeepEvalBaseSystemOneModel도 지정할 수 있다. [공식 문서](https://deepeval.com/docs/metrics-jev-eval), [TypeSafe 연동](https://deepeval.com/integrations/models/typesafe-ai) | 기존 DeepEval 산출물의 별도 생성 경로. AnyJev 패키지와 혼동하지 않는다. 사용자 제공 System One 구현의 호환성과 의미는 별도 검증 대상이다. 기본 TypeSafe 경로를 오프라인·무료로 묘사하지 않는다. |
| DeepEval의 hybrid / system_one | hybrid는 LLM 추출·설명과 설정한 System One 모델의 판정을 결합한다. system_one은 이를 지원하는 지표에서는 설정한 System One 모델(기본 TypeSafe Jev)만 쓰지만, DAGMetric은 과제 노드 때문에 hybrid로 실행되고 GEval은 항상 LLM으로 실행된다. JevEval도 선택한 모드와 무관하게 설정한 System One 모델이 판정한다. [공식 eval mode 문서](https://deepeval.com/docs/evaluation-eval-modes) | 설정 이름만으로 실제 호출·비용이나 점수 의미를 단정하지 않는다. 지표·실효 모드·fallback과 모델 버전을 결과 식별에 포함한다. |

**설계상 추론:** JevEval은
[사용자 제공 DeepEvalBaseSystemOneModel](https://deepeval.com/docs/metrics-jev-eval)을 허용하므로
AnyJev를 연결하는 구현이 기술적으로 가능할 수 있다. 다만 질문·상태·분포·배치 처리·오류 계약의 호환성은 검증하지 않았다. 연결 가능성이
underwrite의 제품 가치를 입증하는 것도 아니다.

버전 주의:
[AnyJev 0.3.0 변경 기록](https://github.com/nokia-applied-research/AnyJev/blob/main/CHANGELOG.md)은
2026-10-06부터 label-trained L1·L2, head, 자동 routing 등을 제거했다고 명시한다. 검색되는 옛 방법 문서나 포크를 현재
정본의 지원 기능으로 세면 잘못된 통합 계획이 된다. 현재 정본은
[nokia-applied-research/AnyJev](https://github.com/nokia-applied-research/AnyJev)이고
Apache-2.0 라이선스다. 모델 가중치·평가 데이터에는 별도 조건이 있을 수 있다.

제작진이 제시한 Qwen3-8B / BANKING77 20선택지 300건에서는 선택지 역순 답변 변경률이 raw 0.230에서 L0 0.073으로,
ECE가 0.240에서 0.184로 바뀌었다. 이는 순서 편향이 줄었다는 한 사례다. **L0가 순서에 완전히 불변하거나 잘 보정됐다는 증거가 아니다.**
저자들도 300건의 위험·coverage 추정 불확실성과 실제 에이전트 루프 밖의 측정을
[제약 문서](https://github.com/nokia-applied-research/AnyJev/blob/main/docs/limitations.md)에
적었다. AnyJev의 “probabilities”라는 API 형식만으로 underwrite의 calibration read를 만들지 않는다.

JevEval의 중요한 경계: Choice의 무점수(None) 선택지 확률이 절반 이상이면 질문을 제외하며, **적용 가능한 질문이 하나도 없을 때 최종
점수는 1**이다. 이는 DeepEval이 정의한 특정 지표의 계산법이다. 이 점수를 underwrite의 근거 충분 또는 승인 상태로 직접 투영하면
부재가 성공이 될 수 있다. 또한 기본 모델 이름 jev-latest는 고정 버전이 아니다.
[공식 계산 설명](https://deepeval.com/docs/metrics-jev-eval)을 참조한다. 문서가 말하는 “결정적 reason”은 같은
질문별 응답에서 같은 문장을 조립한다는 뜻이며, 원격 모델 응답이나 미래 모델 버전이 불변이라는 뜻이 아니다.

TypeSafe의 [confidence 정의](https://docs.typesafe.ai/confidence)는 분포의 집중도를 요약한다. 이것을 사람이
판정한 정답일 확률, 모델 정확도 또는 calibration 증서로 해석할 수 없다. TypeSafe 문서도 임계값을 사용 영역의 데이터로 시험하라고
권한다.

## 더 넓은 판단 모델 연구가 주는 교훈

| 접근 | 1차 근거 | 제품 설계에 주는 뜻 |
| --- | --- | --- |
| 생성형 LLM 판정과 G-Eval | [MT-Bench / Chatbot Arena](https://arxiv.org/abs/2306.05685)는 해당 조건에서 사람 선호와 높은 일치를 보고하며 위치·장황함·자기 계열 편향도 기술한다. [G-Eval](https://arxiv.org/abs/2303.16634)은 서술형 평가의 가능성을 보여준다. [JUDGE-BENCH](https://arxiv.org/abs/2406.18403)는 20개 과제에서 판단 성능의 큰 변동을 보인다. | 설명이 필요한 복잡한 판단에는 유용하지만, 한 도메인의 인간 일치를 다른 도메인의 정답 보증으로 이식하지 않는다. |
| 쌍대·순위 판정 | [Prometheus 2](https://arxiv.org/abs/2405.01535)는 루브릭 기반 점수와 쌍대 판정을 함께 연구한다. [AlpacaEval 길이 통제](https://arxiv.org/abs/2404.04475)는 비교의 길이 교란을 다룬다. [pairwise vs pointwise 연구](https://arxiv.org/abs/2504.14716)는 설정에 따라 쌍대 방식도 교란에 민감함을 보인다. | 변경 후보 A/B를 비교할 때 기존 AB/BA 계산을 활용할 수 있다. 순서 일치가 정답을 뜻하지는 않는다. |
| 보상·전문화 모델 | [RewardBench 2](https://arxiv.org/abs/2506.01937)는 새 사람 판정 자료와 다운스트림 관련성을 강조한다. [Skywork Reward V2](https://arxiv.org/abs/2507.01352)는 공개 모델 후보를 제공한다. | 보상 스칼라를 확률·확인된 성공으로 취급하지 않는다. 벤치마크 상위권은 underwrite 사용자 과제 개선의 선별 정보일 뿐이다. |
| 에이전트 실행 경로 판정 | [AgentRewardBench](https://arxiv.org/abs/2504.08942)는 전문가가 살펴본 1,302개 실행 경로에서 성공·부작용·반복을 구분했다. 규칙은 성공을 놓칠 수 있으나 12개 판단 모델 중 모든 벤치마크에서 최고인 모델도 없었다. | 목표 결과를 “불완전한 실제 실행의 잘못된 통과 감소”로 잡을 이유가 있다. 결과 문장만 있으면 실행 부작용은 확인할 수 없다. |
| 보정·기권·사람 확인 | [StratPPI](https://proceedings.neurips.cc/paper_files/paper/2024/hash/c9fcd02e6445c7dfbad6986abee53d0d-Abstract.html)는 사람 라벨과 자동 판단을 결합하는 층화 설계를 연구한다. [판단 점수 구간 연구](https://arxiv.org/abs/2509.18658)는 특정 조건에서 구간 coverage를 다룬다. | 소수의 독립 라벨을 어디에 쓸지와 미측정·기권 표기를 설계한다. 영역 이동과 표본 선택을 검증하지 않은 coverage 보증은 금물이다. |
| 다수결·저가 모델 연쇄 | [Panel of LLM Evaluators](https://arxiv.org/abs/2404.18796)는 연구 조건에서 패널 이점을 보고한다. 반면 [Jev 대 LLM 사람 기준 비교](https://arxiv.org/abs/2609.29769)는 오류가 겹쳐, 이상적인 임계값으로도 단일 최고 판정보다 정확도 이득이 2.7점 이내였다고 보고한다. | 모델 수를 늘리거나 “저가 판단 → 불확실하면 LLM”을 붙이는 것 자체가 제품 가치가 아니다. 서로 다른 오류를 실제 사례에서 찾았을 때만 조합한다. |
| 입력 공격·영역 밖 | [독립 Jev 실험](https://github.com/willkelly/jev-evaluation)은 지원 티켓 분류에서 ECE 0.075를 관찰했지만, 다른 문제(무작위 3-SAT)에서는 확신한 오답과 권위 사칭 입력의 영향을 관찰했다. [생성형 LLM 판정기 입력 공격 연구](https://arxiv.org/abs/2504.18333)는 입력 조작 위험을 시험한다. | 후보 답변·도구 출력은 신뢰되지 않는 입력이다. 신뢰성 측정에는 출처 혼합, 지시문 주입, 영역 이동을 포함한다. |

[JudgeArena의 2026년 논문](https://arxiv.org/abs/2608.02620) 저자들은 여러 판단 벤치마크를 교체 가능한 모델과
메타데이터 기록을 갖춘 단일 인터페이스로 통합했다고 보고한다. 이 선행 작업을 고려하면 범용 판단 실행기만으로는 차별화가 약하다는 것이 이 조사의
판단이다. underwrite는 후속 검토에서 판단 근거가 적격한지 확인하는 경계에 초점을 둔다. 이는 다른 OSS에 같은 발상이 없다는 증거는 아니다.

표의 숫자는 각각의 과제·모델·실험 설계에서만 해석한다. 공개 논문과 공급자 README가 underwrite의 비교 실험을 대신하지 않는다. “Jev가
빠르다”, “패널이 정확하다”, “순서 회전으로 안전하다” 같은 문장은 사용자 과제에서의 근거가 아니다.

## 제품 후보 우선순위

1. **판단 결과 적격성 대조 실험 (우선).** 실제 에이전트 실행·독립 라벨·현재 underwrite 결과를 같은 사례에 연결한다. 가장 직접적인
   제품 질문은 “현재 자료만 받은 검토자가 안전하다고 잘못 추천한 실패·부작용을, 판단 근거를 제공하면 더 찾아내는가”이다. 원천의 pass 주장과
   underwrite의 분류, 검토자의 후속 추천을 섞지 않는다. 모델 출력 자체보다 연결·누락·적용 여부·확률 의미의 정합성을 먼저 확인한다. 기존
   순수 판단 계산과 로컬 불변 기록을 재사용한다.

2. **근거가 확보된 뒤의 로컬 판단 감사 CLI (조건부).** 실제 사용자가 반복해야 하는 연결·정규화 작업과 오류를 확인한 경우에만 입력을 하나의
   단위로 묶는다. 공급자의 점수를 source claim으로 두고, 독립 라벨 없이는 보정·적격성·승인을 내지 않는다. 적용 질문 0건, 원본 누락,
   점수만 있고 breakdown이 없는 경우를 명시적 불충분 상태로 취급한다. 새 저장소나 별도 웹 서비스는 필요하지 않다.

3. **선택적 모델 실행 연동 (후순위).** 공개 가중치의 로컬 실행은 underwrite CLI의 필수 설치·자원 요구를 크게 바꾼다.
   JevEval의 기본 TypeSafe 경로는 API 키와 사용량 비용 확인이 필요하다. 사용자 제공 System One 구현은 별도 설치·자원·품질
   검증 대상이다. 오프라인 결과 소비가 같은 가치를 만들면 런타임 실행기 내장은 선택하지 않는다.

4. **판단 점수에 따른 자동 수락·배포 (제외).** 현재 사람 검토·승인 분리와 어긋나며, 독립 결과 라벨·모집단·오류율 없이 높은
   confidence만으로 통과시키는 것은 제품 핵심 명제를 위반한다.

이 순위는 구현 승인 목록이 아니다. 1번의 실제 결과가 2번을 필요로 하는지 판단한다. 현재 underwrite의 공개 DeepEval·Promptfoo
샘플은 실제 생산 도구로 만든 파일을 검사하는 용도지만 합성 과제이며, 판단 모델의 의미적 정확도를 증명할 독립 정답 자료는 아니다.
[DeepEval 원천 메모](../../fixtures/golden/external/deepeval-4.2.8/SOURCE.md) ,
[Promptfoo 원천 메모](../../fixtures/golden/external/promptfoo-0.124.1/SOURCE.md) .

## 제품 가치 검증 실험

사전 질문: 독립 정답이 있는 에이전트 실행 사례에서 현재 underwrite 결과만 받은 검토자와, 같은 결과에 검증 가능한 판단 보조 근거를 더 받은
검토자의 **안전 수용 추천 오류와 검토 부담이 어떻게 달라지는가?** 추천은 제품의 승인 출력이 아닌 실험 참가자의 후속 행동이다. 원천 생산자의
pass 주장과 벤치마크의 규칙 평가를 비교할 수는 있지만 이는 별도의 원천·평가기 품질 분석이며 underwrite 자체의 현재 잘못된 승인과 비교하는
실험이 아니다.

1. **자료:** 실제 실행 경로·원본·정답의 연결이 있고 성공·실패·부작용·근거 누락이 함께 있는 사례를 선정한다. 시작 후보인
   [AgentRewardBench 데이터](https://huggingface.co/datasets/McGill-NLP/agent-reward-bench)는
   전문가 주석을 포함하지만 웹 에이전트 영역이며 전체 약 38.4GB이고 제3자 자료 사용 조건이 있다. 전체를 프로젝트 fixture로 복제하지
   않는다. 주석 행 수와 독립 실행 단위 수를 혼동하지 않고, 작은 허용된 부분집합부터 입력 충분성과 사용 조건을 확인한다. 데이터에는 화면 이미지가
   있는 실행도 있으므로 모델별 읽을 수 있는 입력과 공통 텍스트 부분집합을 따로 기록한다. goppi의 후속 실제 실행 결과는 별도 승인·생성 후에만
   추가한다.

   첫 단계는
   [파일 목록](https://huggingface.co/datasets/McGill-NLP/agent-reward-bench/tree/main/data)의
   265 kB `annotations.csv`와 필요한 실행 기록을 확인하는 것이다. 모든 화면 이미지를 내려받지 않고 선택한 trace부터 살펴볼 수
   있다. 다만 주석만으로 판단 모델 평가에 필요한 입력이 충분하다고 보지는 않는다.

2. **독립 정답:** 고정한 루브릭으로 두 명 이상이 모델 판정을 모른 채 성공, 부작용, 미결정, 근거 부재를 표시한다. 의견 차이를 남기고 별도
   합의 기준을 적용한다. 자료 선정·라벨이 시험할 모델 결과를 따라 움직이지 않게 한다.

3. **비교 가능한 입력:** 현행 결정적 감사와 한 생성형 판단 모델, 제한된 선택지 모델(가능하면 AnyJev raw/L0)을 비교한다. 각 경로가
   읽을 수 있는 텍스트·이미지·실행 단계와 결측을 먼저 기록하고, 공통으로 볼 수 있는 사례만 동일 입력·예산의 짝 비교에 넣는다. 지원하지 않는
   양식은 오답 처리하거나 조용히 분모에서 버리지 않는다. 쌍대 순서 교체·패널은 필요할 때만 추가한다. JevEval의 기본 TypeSafe 경로
   사용에는 별도 키·사용 권한·비용 확인이 선행된다. 모델 호출 실패·누락·적용 불가를 성공이나 0점으로 대체하지 않는다.

   검토자 비교에서는 동일한 역할·지침·시간 예산을 고정하고, 사례와 조건 배치를 무작위화하거나 균형 있게 교차 배치한다. 한 검토자가 같은 사례를 두
   조건에서 반복해 보지 않게 하고, 같은 사례를 비교할 때는 서로 다른 검토자에게 나눠 준다. 참조 정답은 검토자에게 숨기며, 사례와 검토자 양쪽의
   변동을 반영한 짝·군집 분석을 계획한다. 그렇지 않으면 검토자 능력이나 재노출 학습을 제품 효과로 오인할 수 있다.

4. **동결할 정체성:** 원본 바이트, 사례/실행/평가기 ID, 사건·루브릭과 질문·선택지/순서·가중치·적용 규칙, 모델의 고정 식별자와 버전, 실행
   설정, 비교할 현재 underwrite 정책과 검토자의 후속 추천 규칙(안전 수용·거절·보류), 전체 대상 모집단, 검토 예산, 기준 임계값을 결과
   보기 전에 기록한다. 기본 jev-latest 같은 이동 별칭은 재현 가능한 모델 버전이 아니다. 선택한 입력은 기존 로컬 기록 계약으로 보존한다.

5. **1차 끝점:** 두 조건의 검토자가 같은 자격의 사례에 대해 남긴 후속 추천 중, 독립 정답상 실패·부작용인데 안전 수용을 추천한 수와 비율.
   사전에 정한 대상 전체와 해당 상태의 분모를 모두 공개하며, 검토 예산 또는 수용 coverage를 고정해 짝 차이와 불확실성 구간을 본다. 독립
   라벨의 미결정·근거 부재는 실패 정답과 섞지 않고 보류와 coverage로 집계한다. 2차로 정상 사례 수용 유지율, 거절·기권·사람 검토율, 질문
   적용률, AB/BA 불일치, 영역별 실패, 설치/메모리/지연/호출 비용을 낸다. Brier/ECE는 모델이 사전에 선언한 바로 그 이진 사건의 결과
   이전 확률, 독립 결과 라벨, 예상 전체 사례와 누락 정보가 있을 때만 계산한다. 충분한 쌍과 ECE 구간별 최소 표본도 정책에 명시하고, 만족하지
   못하면 not_measured로 남긴다.

6. **오류 조건:** 전부 해당 없음인데 점수 1, 일부 기록 누락, 모델 지시문 주입, 근거 제거, 답변 길이 변화, 선택지 역순, 문구 바꿈,
   동률·경계값, 평가 모델 또는 루브릭 변경을 포함한다. 정답 자료와 평가용 홀드아웃은 원천 과제·생성 모델·시간대별로 분리해 누출과 영역 이동을
   확인한다.

7. **채택 기준:** 관측 전 대상 전체, baseline 후속 추천 규칙, 오류 허용량과 검토 예산을 명시한다. 홀드아웃에서 1차 안전 오류의 실제
   감소가 보여야 하고, 정상 수용·기권·검토 비용의 손실도 받아들일 수 있어야 한다. 불확실성 구간, 사례별 판정 차이, 원본 링크를 함께 공개한다.
   보정이 없거나 범위 밖이면 해당 검사를 not_measured로 기록한다. 수치가 유리해도 자동 병합 권한은 주지 않는다.

첫 실험의 결과가 “동일한 사례에서 값이 없다”라면 어댑터를 만드는 대신 어떤 입력·독립 라벨·적용 정보가 부족했는지 출력하는 것이 진전이다. 반대로
검토자의 실제 잘못된 안전 추천을 더 찾아내고 불필요한 검토가 늘지 않는다면, 공급자별 모델 실행보다 **검증된 판단의 근거를 다루는 공통 로컬 감사**가
underwrite만의 제품 가치가 된다. 이것은 현재 자료에 기초한 설계 가설이며, 시장에 유일하다는 주장이나 검증 완료 선언은 아니다.

## 이번 조사에서 확인하지 못한 것

- AnyJev나 JevEval을 underwrite의 실제 사용자 사례에 적용했을 때의 오류 감소·지연·사용자 시간·비용. 모델 실행이나 사람 라벨
  수집을 하지 않았다.

- JevEval score_breakdown이 DeepEval의 로컬 TestRun JSON에 실제로 어떤 필드로 남는지. 런타임 객체 문서가 영속
  export 계약과 같다고 가정하지 않는다. 향후 입력 어댑터를 고른다면 정확한 버전의 실제 파일 한 건이 선행 조건이다.

- 공개 AgentRewardBench의 작은 부분집합이 underwrite와 goppi의 사용 과제를 충분히 대표하는지. 웹 에이전트 성과를 코드
  에이전트/평가 하네스 전체로 일반화하지 않는다.

- underwrite가 다른 OSS보다 유리하다는 실사용 비교. 동일 사용자 과제, 입력, 신뢰 조건의 비교가 필요하다.

판단 기반 모델은 중요한 **증거 생산자와 비교 대상**이다. 현 시점의 제품 방향은 판단이 맞을 자격이 있는 조건과 실패·보류·근거를 사용자가 안전하게
확인하도록 만드는 것이다.
