# 결과·원자료·외부 검증을 잇는 Underwrite 작업 방법론 계획

작성일: 2026-10-28. 근거와 비판적 판단은
[리세버그 인터뷰 연구](../research/FELIX_RIESEBERG_AGENT_DELEGATION.ko.md)에 있다.
이 계획은 개발·평가 방식을 시험하는 **계획**이다. 새 제품 기능의 구현 완료,
사람의 시간 절감, 모델 판단의 정확도, Goppi의 새 인계 준비를 선언하지 않는다.

## 목표와 바꾸지 않을 경계

목표는 사용자가 가진 완료된 평가 자료를 에이전트가 적은 왕복으로 바르게 읽고,
**검증되지 않은 결과가 검증된 것으로 통과하지 않으면서** 다음 필요한 근거·행동을
제시하는 것이다. 개발 작업에서도 사용자의 결과를 먼저 정의하고, 실제 원자료와
해당 분야의 방법을 사용하고, 작성 세션 밖의 확인으로 끝낸다.

기존 [저장소 지침](../../AGENTS.md), [구현 소유권](../../CONTRIBUTING.md#implementation-owners),
상위 작업공간의 `AGENTS.md`가 적용될 때 그 반복 루프는 유지한다.
Underwrite는 생산자 간 근거 의미·
비교 가능성·결측·다음 검증 과제를 소유한다. Goppi는 원생 실행·trace·검증기 결합·
제안·통제 재실행을 소유한다. 해시=바이트 동일성, 출처 주장, 독립 인증,
측정과 채택 권한은 서로 다른 판단이다. `not_measured`, `indeterminate`,
`abstained`를 하나의 성공/실패로 접지 않는다. 이 계획은 Docker·서버·웹 앱,
상시 모델 심판, 자동 승인, provider 실행, 버전 변경을 요구하지 않는다.

### Goppi의 별도 방법 파일럿과 맞추기

Goppi `main`에 수용된 [영상 연구](https://github.com/ntts9990/goppi/blob/5d61832b4b4799c83e2af43d1a89f1c4274fd6ec/docs/research/FELIX_DELEGATION_METHODS_GOPPI.ko.md)와
[파일럿 계획](https://github.com/ntts9990/goppi/blob/5d61832b4b4799c83e2af43d1a89f1c4274fd6ec/docs/plan/OUTCOME_METHOD_EXTERNAL_VERIFICATION_PILOT.ko.md)은
**스킬·하네스의 지시문 H1이 H0보다 독립 과제의 행동 성과를 개선하는가**를 묻는다.
계획은 실제 대상·검증기·예산을 아직 봉인하지 않았다. 기존 D 수집기·저장·
예정 단위 ledger·final-access 상태 기계·짝비교 계산 소유자는 재사용 후보로
존재한다. **새 고정 H0/H1 계약·closure·Pi 최종 T adapter·통합 실행 경로**는
미구현이다. 이 상태를 Underwrite의 새 입력 형식이나 완료된 효능으로 승격하지 않는다.

| 분리된 연구 | 바꾸는 것 | 주 분석 단위·결과 | 별도 범위 |
| --- | --- | --- | --- |
| **Goppi 방법 지시 효과** | 같은 실행 조건에서 스킬·하네스의 H0 대비 H1 지시 한 구역 | 독립 T 사례의 repeat 0에서 짝지은 이진 행동 결과 H1−H0 | 실패 전이는 위험 guardrail, 결측·비용은 별도 회계. 실행·비공개 최종 자료는 Goppi grant와 사람 결정에 종속. |
| **Underwrite 작업 준비·방법 파일럿** | 완료된 산출물을 읽는 동일 과제에서 현행 방식 대비 네 질문으로 결과·원자료·도구·확인을 먼저 명시 | 사전 고정한 작업 세션별 올바른 근거·한계·다음 행동과 사람 활동시간 | 원본 바이트·CLI·권한은 동일. 이 방법의 효과를 출력 표시의 효과와 섞지 않음. |
| **Underwrite 출력 표시 연구** | 동일한 완료 근거를 현행 CLI/JSON, 직접 링크, 기존 기록에서 파생한 요약으로 제시 | 사전 고정한 검토 세션별 정확한 해석, 잘못된 승인/반려와 사람 활동시간 | 세 조건의 원천·권한은 동일. 파생 요약은 새 정답이나 채택 권한을 만들지 않음. |

각 연구의 분모와 효과 추정은 합산하지 않는다. Underwrite의 분모는 사전 고정한
작업·검토 세션이지 fixture 항목, 생산자 행 또는 반복 수가 아니다. Goppi 파일럿 결과를
Underwrite의 사용자 효율 근거로 대신 쓰지 않고, Underwrite가 본 구조적 일치를
Goppi의 원생 실행 인증으로 되돌려 말하지 않는다. 새 교환 형식이 생기면 수용된
원본·fixture와 검증 경계를 확인한 뒤에만 기존 어댑터로 충분한지 판단한다.

## 작업 시작의 작은 결정 틀

새 생산자 계약, 비교 가능성·출처·권한 판단, 되돌리기 어려운 결과처럼
해석 위험이 있는 과제에서만 기존 이슈·PR 설명 또는 작업 기록에
다음 내용을 **한 번** 적는다. 별도 양식 파일·필수 게이트·새 스킬을 만들지 않는다.
명백한 작은 수정은 기존 회귀 테스트와 preflight 경로로 바로 간다.

| 질문 | 기존 의미 소유자와 답의 형태 | 잘못된 답의 신호 |
| --- | --- | --- |
| 무엇을 이루려는가? 뛰어난 실무자는 빠뜨린 단계를 무엇이라 볼까? | 사용자 과제와 완료 기준, 결과의 사용자를 먼저 적는다. 생산자 실행과 Underwrite 해석을 나눈다. | “리포트를 만든다”, “모듈을 추가한다”만 있고 사용자의 판단·행동이 없다. |
| 어떤 원자료에서 시작하는가? | 선택한 로컬 바이트·계약·fixture·출처와 접근 권한, 모집단·결측을 기록한다. 원본을 모두 프롬프트에 복사하지 않는다. | 집계 숫자만 있고 사례·반복·원본 범위가 없거나 입력 지시문을 권한으로 취급한다. |
| 어떤 실제 기법·도구가 필요한가? | 해당 구성개념의 정본 계산, CLI/API, Goppi 원생 검증, 부정 사례, 독립 리뷰 중 필요한 것만 선택한다. | “전문가처럼”이라는 역할 문장만 있고 실제 계산·도구·판정 경계가 없다. |
| 모델·요청자 밖에서 무엇으로 확인하는가? | 재현 가능한 명령과 기대 결과, 원본·환경 상태, 사람 검토가 필요한 판단을 분리한다. | 작성자가 자기 결과를 승인하거나 모델 간 합의·해시만으로 진실을 선언한다. |

이 틀은 **질문을 실행하는 사람/에이전트의 작업 지도**이며 제품 JSON의 새
필수 필드가 아니다. 현재 `audit-trajectory`의 모집단·`trust_scope`·다음 과제와
`review-artifacts`의 비교 불가 사유를 먼저 소비한다. 자료를 연결하면 풀리는
문제에 새 계산기나 “전문가 에이전트”를 만들지 않는다.

예를 들어 “Goppi 후보가 나아졌나?”라는 요청은 먼저 **같은 사례·단계·반복의
도구 상태와 검증기 결과 중 무엇이 바뀌었는가**로 좁힌다. 완전한 paired+trajectory
원본과 설치된 호환 Goppi 오프라인 검증기를 선택하고, Underwrite의 기존
`audit-trajectory`가 같은 바이트의 임시 복사본을 검증·기술 비교하게 한다.
`read` 도구의 error 상태와 결과 false가 `read` 도구의 ok 상태와 true로
함께 바뀌어도 호출 관계가 없으면 원인·재시도 효과는
미측정이며, 다음 행동은 필요한 관계 근거의 수집이다. 이 예시는 합성 fixture의
해석 경계이지 실제 후보의 개선 증명이 아니다.

## 단계별 실행

| 순서 | 작업과 소유자 | 산출물·검증 근거 | 다음 단계로 가는 조건 |
| --- | --- | --- | --- |
| **0. 기준선 봉인** | Underwrite 개발 담당이 실제로 반복되는 과제 유형 하나를 고른다. 최근 기록에서 원자료·명령·리뷰·수정 왕복을 찾아 정의한다. | 같은 문제에 대한 현재 방식의 입력, 결과 JSON, 원본 위치, 권한, 에이전트·사람의 단계 목록. 과거 사람 시간을 재구성하지 못하면 파일럿 기록에 `미측정(회고 복원 불가)`로 표시한다. | 문제와 완료 기준이 구체적이고 현재 명령/스킬로 답할 수 있는 범위를 확인. |
| **1. 네 질문 파일럿** | 같은 소유자가 기존 작업 기록에 위 결정 틀을 적용한다. 첫 대상은 다음 실제 결함 하나와 완료된 평가 파일 하나로 제한한다. | 결과물, 사용한 원자료, 선택한 도구/방법, 외부 확인 기준. 기존 방식보다 추가된 사람·에이전트 단계를 기록. | 유용한 새 근거 또는 오판 방지가 관찰되고 권한·비용 범위를 지켰다. 없으면 원상 복귀. |
| **2. 적대적 검토·판정** | 작성자와 다른 리뷰어가 사실·구성개념·입력 경계·누락 반례를 공격한다. 작성자는 실제 재현과 정본 계약으로 각 지적을 수용·기각·미결정한다. | 지적마다 `판정: 수용 / 기각 / 미결정`과 `근거 상태: 재현됨 / 재현 불가 / 해석 불명확`을 분리하고 입력·명령·기대와 실제 출력을 남긴다. 비평 수나 모델 합의를 품질 점수로 세지 않음. | 신뢰·개인정보·정확성 결함은 해결. 독립 확인이 불가능한 주장은 미측정으로 남김. |
| **3. 현행 사용자 경로와 나란히 비교** | 완료된 실제 파일이 확보되면 호출 에이전트와 사용자가 현행 CLI·직접 링크 보강·기존 기록에서 파생한 요약을 유사 과제에서 비교한다. 이 영상의 네 질문은 과제 준비에 쓰되 세 출력 조건의 증거와 권한은 같게 둔다. | 사용자가 올바른 명령·원본·한계·다음 근거를 찾는 시간과 오류. 합성 fixture는 부정 사례로만 사용. | 직접 링크로 충분하면 요약을 만들지 않음. 파생 요약이 추가 가치를 보일 때만 기존 결과 owner에서 검토. |
| **4. 정책·제품 반영 결정** | 리드가 파일럿과 리뷰 근거를 종합한다. 효과가 확인된 최소 규칙만 기존 `CONTRIBUTING.md`, 리뷰 스킬 또는 결과 계약의 정본 owner에 반영한다. | 변경 전후 사용자 단계, 의미 정확도, 유지보수 비용, 해당 회귀·CLI 검사, 별도 리뷰와 최종 preflight. | 외부 근거와 실제 사용자 과제가 없으면 추가 정책·제품 기능을 보류. |

단계 0의 과거 기록은 오류 위치와 비용 항목을 고르는 **형성적 자료**다.
시간·정확도 효과를 검정하는 대조군으로 소급 사용하지 않는다. 단계 1·2는
로컬에서 승인된 기존 작업만 다룬다. 단계 3에서 에이전트/모델을 실행하거나
실제 사용자 자료를 사용할 때는 해당 예산·개인정보·권한이 별도로 성립해야 한다.
이 문서 자체가 그 실행을 승인하지 않는다.
파일럿을 실제 시작하기 전에는 별도 작업 기록에 대상 과제·원본 artifact,
조건 배정과 순서, 오류 판정 기준, 의미 있는 개선 및 중단 기준을 선고정한다.
그 대상이나 기준이 없으면 단계 1·3의 효과를 측정했다고 쓰지 않는다.

## 대조에서 기록할 값과 실패 기준

실험 전 과제, 입력 바이트·모델·도구·권한·예산, 성공 기준과 부정 사례를 고정하고
조건 순서를 기록한다. 소수 사례는 사용성 문제 발견용이며 일반화된 효과 추정이
아니다. 결과 표에는 다음 값을 섞지 않고 둔다.

- **정확성:** 같은 구성개념·사례·반복·정책을 맞게 식별했는가, 결측·원천 주장·
  독립 확인·승인 권한을 혼동했는가, 잘못된 승인과 불필요한 반려가 있었는가.
- **작업 비용:** 사람의 실제 활동시간, 전체 경과시간, 리뷰 대기, 도구 대기,
  에이전트 실행시간·토큰을 구분한다. 중첩 구간을 중복 합산하지 않는다.
- **유지보수:** 소유자 탐색, 리뷰 왕복, 기각된 적대적 지적, 정책/스킬 수정과
  그 후의 재작업, 새 설명·게이트의 동기화 비용을 기록한다.
- **외부 확인:** 원본/독립 정답 또는 실제 환경 상태, 결정적 검사, 사람의 교정
  범위를 표기한다. LLM 심판은 근거 검색·지적 우선순위에 쓸 수 있지만 정답을
  자동 생성하지 않는다.

반례는 특히 `all-pass`처럼 보이는 원천 선언, 일치하는 해시와 거짓 출처 주장,
같은 이름의 다른 지표, 계획 모집단 부재, 미포착 trace의 0회 호출, Goppi의
도구 오류 감소와 결과 개선의 우연한 동시 발생을 포함한다. 원본이 없는 성공
판정, 부정확한 비교 가능성, 개인 정보 누출, 승인 없는 실행은 즉시 실패다.
사람의 시간이 줄더라도 잘못된 승인이 늘거나 새 오류를 설명·복구하지 못하면
방법을 확대하지 않는다. 더 긴 프롬프트·더 많은 리뷰어·더 많은 기능은 목표가
아니다. 파일럿 전에 의미 있는 개선 기준을 정하되, 작은 표본에서 통계적 우월성을
주장하지 않는다.

## 현행 루프에 넣는 위치와 중단 조건

작업 흐름은 `사용자 결과 확인 → 원자료·소유자 확인 → 작은 계획 → 구현 →
실행 재현·부정 검사 → 별도 적대적 리뷰 → 리팩토링 → 최종 로컬 preflight →
다음 증거 기반 작업`이다. 네 질문은 앞의 **결과·원자료·방법·확인 기준을
명확히 할 때만** 사용한다. 저장소의 기존
[preflight 스킬](../../.codex/skills/underwrite-preflight/SKILL.md)은 최종 변경 뒤
계속 적용한다. 코드·계약 변경 때는 집중 회귀와 실제 진입점을 먼저 확인한다.
문서만 바뀌어도 정본 runner의 선택 결과를 읽는다. 새 강제 게이트나 CI 예약 실행을
만들지 않는다.

Goppi 인계가 실제로 바뀌면 수용된 `main` 원천·실제 fixture·내용 해시와
오프라인 검증을 먼저 본다. 단순 `candidate_on_main`, 파일명 변화, 모델의
“준비됐다”는 설명은 수용 근거가 아니다. Underwrite가 이미 구조화해 내는
상태·모집단·한계·다음 과제가 사용자의 질문에 답하면 제품 코드를 추가하지 않는다.
필요한 관계 데이터가 없으면 Goppi에 **어떤 원생 관계를 남겨야 하는지**를
다음 과제로 돌리고, Underwrite가 순서·이름으로 인과를 추측하지 않는다.

이번 계획의 현재 완료 상태는 **자료 조사와 방법 설계**다. 실사용 과제에서의
시간 절감·판단 개선, 네 질문을 상시 지침으로 승격할지, 결과 JSON을 바꿀지는
미측정이다. 후속 구현은 위 단계의 관측 차이가 생긴 최소 범위에서만 시작한다.
