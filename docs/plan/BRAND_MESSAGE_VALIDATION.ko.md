# Underwrite 브랜드 메시지와 첫 사용 검증

기준일: 2026-10-29. 이 문서는 제품 범위를 바꾸거나 배포를 승인하지 않는다.
현재 PyPI 앱 배포판은 0.2.0, 코어 배포판은 0.1.1이다. 저장소의
0.2.0 코드에는 배포 후 개발 변경도 있으므로 기능은 실행 파일의
`capabilities --json`으로 확인한다.

## 기억시킬 일

> 평가는 끝났습니다. 그 결과로 어디까지 말할 수 있나요?

Underwrite는 **지원하는 완료된 로컬 평가 파일**에서 확인된 사실, 부족한 근거,
다음 확인 과제를 에이전트가 읽을 수 있는 JSON으로 반환한다. 생산자 실행,
정답 인증, 범용 점수, 병합·배포 승인은 약속하지 않는다. 로컬 CLI와 Python
API의 파일 기반 경로에는 서버나 모델 호출이 필요하지 않다.

영문 첫 문장: “The eval finished. What can you actually claim?”
GitHub About 후보: “Review supported agent eval files: find mismatches, keep
missing evidence visible, and know what to check next.”

브랜드의 목표는 **새 사용자가 자기 파일을 올바르게 검토하고 다음 근거를
찾는 것**이다. 스타·다운로드·README 클릭은 발견의 보조 지표이지 목표가
아니다. 오판이나 근거 없는 승인 주장이 늘면 첫 사용이 빨라져도 실패다.
이는 [Alex Schultz의 목표·지표·증분 효과 구분](https://medium.com/%40AnalyticsAtMeta/beyond-the-numbers-metas-cmo-and-vp-of-analytics-alex-schultz-on-career-shifts-and-the-ai-30d52ba6ebfa)을
제품에 적용한 가설이며 Underwrite의 성장 효과를 측정한 결과가 아니다.

## 사용 상황과 노출 위치

같은 약속을 세 상황에 반복한다. ① 평가 요약과 제공된 행이 다를 때,
② 두 산출물이 같은 사례·조건을 비교하는지 확인할 때, ③ 에이전트가
`pass`라고 했지만 빠진 근거를 찾아야 할 때. 각 예시는 실제 지원 명령,
선택한 파일의 신원, `unknown`과 다음 확인 작업을 함께 보여준다. 지원하지
않는 파일도 임의로 비교할 수 있다고 쓰지 않는다.

GitHub About은 한 문장, README 첫 화면은 한 상황과 결과, 설치·스킬
안내는 그 결과에 도달하는 짧은 경로를 담당한다. 현재 PyPI 0.2.0의
설명은 배포된 아티팩트에 묶여 있다. 이 저장소의 메타데이터 변경은 다음
버전 배포를 사용자가 승인할 때만 공개된다. 로고·이름·첫 문장을 일관되게
사용하되, 기능상 독점이나 출처 인증은 주장하지 않는다.

세리자와 렌의 [원서 공개 서문](https://bookplus.nikkei.com/atcl/column/032900009/121400497/)과
[저자 인터뷰](https://marketingnative.jp/keyperson04/)는 충성 팬·차별화에
관한 직관을 검증하고, 수요가 생기는 상황에서 떠올리고 찾기 쉬운 브랜드를
강조한다. 이를 **좁은 제품 책임을 여러 실제 검토 상황에서 찾기 쉽게 한다**는
가설로 적용한다. 원서 [출판사 소개](https://bookplus.nikkei.com/atcl/catalog/23/11/28/01123/)는
혁신적 새 시장을 주된 적용 범위로 삼지 않으므로 소비재 성장 수치를
개발자 OSS의 예상 효과로 옮기지 않는다.

## 첫 사용 관찰 계획

공개 설명을 바꾼 뒤에도 효과는 미측정으로 둔다. 외부 평가 파일을 다뤄본
개발자 6–8명을 편의 모집해 형성적 관찰을 한다. 두 첫 화면 문안(이전
기술 설명 / 문제 상황과 출력 예시)을 참가자별로 순서를 바꿔 보여주고,
짧은 노출 뒤 다음을 묻는다.

1. Underwrite가 하는 일과 하지 않는 일을 각각 설명할 수 있는가?
2. 제공된 합성 Promptfoo 파일에서 어떤 명령을 선택하고, 결과의 불일치와
   알 수 없는 원인을 분리하는가?
3. 실제 자기 파일을 다룬다면 무엇을 추가로 확인해야 하는가?

정확한 설명, 첫 지원 명령까지의 단계·시간, 잘못된 승인/검증 주장, 원본
확인 행동을 따로 기록한다. 참여가 자발적일 때만 최소한의 비식별 기록을
보관하며, 비공개 평가 파일·토큰·모델 호출은 요구하지 않는다. 작은 표본의
차이는 문안 개선 신호일 뿐 인과적 성장 효과 추정이 아니다. 이전 문안과
차이가 없거나 오판이 늘면 더 단순한 문안을 택한다. 필요할 때만 동일한
사용 과제·권한에서 더 큰 비교를 계획한다.
